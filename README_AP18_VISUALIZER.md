# AP18 可视化分析程序

## 架构（形态 B：前后端分离 + 后端无状态解析）

- **前端**：`web/index.html` + `web/style.css` + `web/app.js`，独立静态站点，不再内嵌在 Python 里。
- **后端**：`ap18_visualizer.py` 做三件事——把 `web/` 静态资源发给浏览器、提供一次性解析 API `POST /api/parse`、提供有效里程 API `POST /api/mileage`。
- **无状态**：浏览器把所选 `.pcap` / `.txt` 上传后，后端解析完把结果 JSON 返回，**不保存任何数据集**（临时文件随请求结束删除）。唯一例外是有效里程：它按用户填写的**服务器本地目录**读取数据（独立页面 `/mileage.html`），不参与上面这条无状态上传流程，可用 `--no-mileage` 关闭。
- **有效里程是独立窗口**：单独页面 `web/mileage.html` + `web/mileage.js`，从首页右上角「有效里程」按钮开新窗口，不挤在原分析页里。

> **仓库里不带采集数据**：`AP18/` 之类的 pcap 目录只是历史上的示例（已被清掉），
> `tests/` 下的脚本默认数据目录写的是它，找不到时会提示你把采集目录作为参数传进来，例如
> `python tests/test_parse_api.py --files 3 "D:\你的采集目录"`。

`tests/` 下的 Python 脚本都先 `from _repo import ...`：这样从仓库根目录、从 `tests/` 里、
或者从其它工作目录调用都能正确导入后端模块，并把相对路径按仓库根目录解析。

- **多用户互不影响**：解析后的数据全部保存在各自浏览器内存中（表格、图表、下载、文件夹监控都发生在当前浏览器），多人同时使用不会互相覆盖或影响对方视图；没有服务端共享数据集，也没有“清空并刷新影响所有人”的问题。

### 解析吞吐（加速改造）

改造前每一批文件都在 HTTP 处理线程里串行解码，而 `decode_file` 是纯 Python CPU 密集循环，
被 GIL 串行化后多核等于闲置；整批 rows 还以未压缩 JSON 回传。现在：

| 手段 | 位置 | 作用 |
| --- | --- | --- |
| 多进程解码 | `ProcessPoolExecutor`（`decode_pcap_worker` / `parse_txt_file`），进程数按 CPU 核数自动选择（4 核以下留 1 核给父进程，上限 8） | CPU 密集段真正并行 |
| 前端批内并发 | `web/app.js` 的 `MAX_PARALLEL_BATCHES = 4` | 不再“等一批回来再发下一批”，填满后端进程池 |
| 响应 gzip | `send_bytes(..., gzip_ok=True)`，仅当响应 ≥ 1 MiB 且客户端声明 `Accept-Encoding: gzip` | JSON 文本压缩比通常 8~12×，直接砍掉回传体积 |

顺序保证：进程池结果按**上传下标**回填（不是按完成先后），同一批内仍由服务端 `gps_sort_key` 排序；
跨批次由前端在合并后重新全局排序，因此并发完成顺序不影响最终结果。

### 分批到达就分批渲染（不等全部批次）

以前前端 `await Promise.all(所有批次)` 之后才渲染一次：305 个文件要 80 秒以上，这段时间界面上
什么都没有。现在**任何一批解析完就立刻并入视图并重画**（`absorb` + `renderProgress`）：

- 文件列表每次按**批次下标**重建 → 与上传顺序一致，还没到的批次先不出现；
- 行用**双指针归并**（`mergeSortedRows`，每批内部服务端已排好序）→ 曲线 x 轴、
  悬停二分查找依赖的全局有序性始终成立，不用每次重排 180 万行；
- 中间渲染按 `PROGRESS_RENDER_MS = 1500ms` **节流**（整份数据每并入一次都要重建
  fileRows/trackSegments/统计/降采样并重画地图与轨迹），收尾那一次一定渲染；
- 中途渲染不弹横幅（`applyParsed(..., {banners:false})`），结论只在收尾时给，避免中途的
  "失败/保留原视图"被最后一批推翻；
- 状态栏实时写"正在解析 N/M 个文件…（已显示 X 个文件 · Y 行）"。

实测（headless Chrome，真实数据）：60 个文件首屏数据 **6.8s** 出现，全部 14.9s 完成；
28 个文件量级下 1~3 秒即可看到曲线和轨迹。

新增/变化的取舍（都是有意为之）：

1. **加载过程中文件颜色下标可能挪动一次**：后到的批次会把更靠前的文件插进列表，而颜色按
   列表下标取。加载完成后完全稳定；换来的是不用干等最后一批。
2. **地图视野会被重新 fit 若干次**：每并入一批轨迹范围变大，地图会重新缩放到全部轨迹。
   加载过程中会看到几次跳变。
3. **中途渲染会重置交互状态**：搜索词、分页、选中点在每次中途渲染时回到默认
   （整份数据换了，这是必然的）。
4. **单批延迟仍是首屏瓶颈**：首屏时间 ≈ 第一批的解析+回传时间（约 1~7 秒，取决于服务端并发），
   不是整个目录的时间。

`--workers N` 可以覆盖解码进程数（例如内存紧张时 `--workers 2`）：

```powershell
python ap18_visualizer.py --workers 8 --open
```

加 `--verbose` 后，服务端每处理一次 `/api/parse` 会打印一行证据，可以直接看到每次请求的文件数、
行数、实际并行度、解码耗时和**线上传输体积**（`gzip` 表示已压缩，`raw` 表示未压缩）：

```text
[parse] 8/8 文件 · 48,040 行 · 并行=8 · 解码+合并 4.83s · 总计 5.21s · gzip 2.10 MB
```

对照方式：同一批文件用 `--workers 1` 再跑一次，这一行里的"解码+合并"就是改造前的串行耗时
（前端并发度不变的情况下，两者之比就是多进程实际拿到的加速比）。

## 性能量测与自检

开发和验证脚本都放在 `tests/` 下（它们不参与部署），在仓库任意目录执行都可以，不需要额外依赖。
**需要采集数据的用参数指定目录**（仓库不带数据，见上一节的说明），不带参数时只有前端那几个 DOM stub 自检能跑：

```powershell
node tests/check_syntax.js                   # 交付自检：Python/JS 语法 + 关键实现点静态断言（不需要数据）
node tests/test_frontend_faults.js           # 前端自检：分批渲染/失败容错/勾选置灰/地图视角（DOM stub，不需要数据）
node tests/test_frontend_stats.js            # 前端自检：位置 RMS 超限比例的统计口径（不需要数据）

$DATA = "D:\你的采集目录"                     # 下面这些都需要一份 pcap 数据
python tests/test_parse_api.py --solo "$DATA"      # 端到端自检：多进程回填 / gzip 协商 / 逐字段一致
python tests/test_fault_tolerance.py "$DATA"       # 容错自检：好文件与 8 种坏文件混在同一批里
python tests/bench_pipeline.py --limit 4 "$DATA"   # 逐段计时：串行解析 / 多进程 / multipart / JSON+gzip
python tests/bench_concurrency.py --limit 16 "$DATA"  # 真实 HTTP 路径：串行逐批 vs 并发 4 批
python tests/check_track.py "$DATA"                # 轨迹质量诊断（经度跨度、野点、跳变、状态分布）
python tests/diagnose_pcap.py "$DATA\xx.pcap"      # 单文件诊断：这份数据到底能画出哪些图
node tests/check_browser_render.js --data "$DATA" --count 28   # 真浏览器渲染自检（无头 Chrome + 读画布像素）
```

- `bench_pipeline.py` 打印单批各阶段耗时与占比，并给出“多进程能拿到几倍加速”（[2] 相对 [1]）与“每行多少字节”（[4]）两个决策数字；`--json out.json` 可留档对比改造前后。
- `test_parse_api.py` 起一个临时端口服务，分别用 `Accept-Encoding: identity` 和 `gzip` 各请求一次，
  确认 gzip 只在预期条件下启用、两种编码的 rows 完全相同，并把响应 rows 与直连 `decode_file()` 的结果
  逐字段比对。`--solo` 会额外用 `--workers 1` 再跑一遍（单进程队列最容易暴露“按完成顺序回填”这类错误），
  `--verbose` 会一并打印服务端的每次请求耗时行。任何一项失败都会打印 `[FAIL]` 并返回非零退出码。

### 验收清单

1. `python tests/test_parse_api.py --solo` → `结果：全部通过`（正确性：数据与改造前逐字段一致）；
2. `python ap18_visualizer.py --verbose --open`，在页面上选一个目录 → 日志出现 `[parse] ... 并行=N ... gzip x.xx MB`；
3. 同一批文件改用 `--workers 1` 再选一次 → 两次的“解码+合并”秒数之比就是多进程的实测加速比。

### 实测结果与当前瓶颈（2026-09 实测，16 核机、AP18 目录）

`tests/bench_pipeline.py`（服务端各段）与 `tests/test_parse_api.py --verbose`（真实 HTTP 路径）：

| 指标 | 实测值 |
| --- | --- |
| 全部 20 个 pcap | 113,768 包 / 112,740 行 / 单文件解码中位 102 ms（约 57,000 包/s） |
| 多进程解码 | 1.95 s → 0.88 s，**2.21x**（16 进程）；HTTP 单批 8 文件内部 0.52 s → 0.24 s |
| 单批 8 文件请求总计 | 约 1.6~1.7 s |
| 其中：多部分解析 | 0.17 s |
| 其中：解码+合并 | 0.45~0.78 s |
| 其中：**JSON 编码 + gzip** | **0.86~1.10 s（约 60%，当前最大头）** |
| 回传体积 | JSON 46.2 MB → gzip 10.3 MB（4.5x）；**1,021 字节/行** |
| 浏览器侧（单批） | 解压 93 ms + `JSON.parse` **531 ms** |
| 端到端（20 文件、8/批） | 串行逐批 6.1~6.8 s vs 并发 4 批 5.6~5.7 s = **约 1.1~1.2x** |

结论：**多进程解码本身是有效的（2.2x），但它只占请求时间的约三分之一**，端到端因此只有 1.09x。
瓶颈已经从“CPU 解码”转移到了**逐行 JSON 的序列化与回传**（服务端编码 + gzip、浏览器解压 +
`JSON.parse`、以及 1 KB/行的体积），而这三项都在各自进程的主线程序列执行。
下一步要拿数量级收益，必须减少**每行字节数**（列式/二进制传输），而不是继续加进程。

### 部分文件失败的容错行为

同一批次里只要有**一个**文件坏掉，绝不会影响其它文件。这条链路由四层保证，并有专门的测试
（`python tests/test_fault_tolerance.py`，构造空文件、截断头、magic 错误、全 0 文件头、pcapng、
包长度越界、伪装成 .pcap 的文本共 8 种坏文件混在好文件里）：

| 层 | 行为 |
| --- | --- |
| 单个畸形 GSOF 记录 | `decode_file` 内部 `try/except` 计数跳过，同一文件的其它记录照常解析（`invalid_records`） |
| 单个坏文件 | 进程池任务在工作进程内捕获异常；该文件进 `errors`（**一行人话原因 + 抛出位置**），其它文件不受影响 |
| 整批请求 | 坏文件**不会**升级为请求级失败：仍返回 HTTP 200，只是 `files` 里少一个、`errors` 里多一条 |
| 全批都坏 | 仍返回 200 + `rows: []` + 每个文件一条 `errors`（不是 500，前端可据此提示） |
| 同名文件 | 服务端给重名文件加 ` (2)` 后缀（`unique_name`），`errors` 与 `_source_file` 因此互不覆盖；前端按去重名映射回原始 `File`，下载仍然可用 |
| 空文件 / 全 0 文件头 | 报 `pcap 全局头不完整（只读到 0 字节，需要 24 字节）`、`文件头前 4 字节全为 0：文件可能正在录制` 这类可读原因。抓包工具刚创建、还没写入内容的文件（magic=`00000000`）是最常见的一种，直接点出来省得当成程序 bug |
| 一个可用文件都没有 | **保留原有视图**：以前这里会无条件替换，结果是选到一个坏 pcap 就把整页图表清空、只剩一条错误横幅。现在旧数据与图表原样保留，横幅与状态栏说明"已保留原有视图（N 个文件 / M 行），如需清空请点清空并刷新" |
| 失败文件在列表里的位置 | 解析失败的文件**也会出现在左侧文件列表**里（末尾、灰色 + 删除线 + "解析失败"，悬停显示原因），但**不可交互**：没有复选框，因此不会被勾选、不会进图表/表格/下载，也不会进文件下拉框与"高亮段数"计数；侧栏概览会额外标出"N 个解析失败（无数据）" |
| 部分批次请求失败 | 成功的批次照常显示，状态栏标出失败批次数并在提示里点名是哪几个文件；**只有全部批次都失败**才保留原视图并报错 |
| 文件夹自动监控 | 只认"文件集合"变化（新增/删除），正在录制的文件变大不触发；两次自动重解析至少间隔 20 秒。否则一个正在录制的 pcap 会让每次轮询都判定"变了"，305 个文件的整目录重解析（80 秒以上）一轮接一轮，页面永远停在"正在解析"、图表一直不显示 |
| 前端处理异常 | 与请求失败区分：请求失败报“解析请求失败”，代码异常报“前端处理出错（请反馈这条信息）”并打印 `console.error`，不会被伪装成网络问题 |

错误文本的取舍：**数据问题**（空文件、magic 不对、截断、不是 pcap）只回传一行原因
（`ap18_visualizer.failure_text`），因为界面上真正有用的是"哪个文件、为什么"，而不是十几行
内部栈帧；**解析器自身的 bug**（AttributeError/KeyError…）仍然回传完整 traceback，不会
被伪装成"文件坏了"。前端的错误横幅还会再压一道：整段 traceback 只保留"文件名 + 最后那句
异常 + 文件:行号"，完整原文放在 `title` 里悬停可看（`errorDetail`）。

### "解析成功但所有图表空白"这类失败

还有一类失败不会报错，只是**什么都画不出来**，排查时最容易走弯路：

1. **字段全空**：GSOF49 的行是有的（`decode_file` 只为 GSOF49 建行，所以"成功"的文件必然有行），
   但位置/速度/姿态这些字段的值是 `NaN`/`Infinity` —— 设备输出配置、GSOF49 页号或字段掩码变了，
   解析器按固定偏移读到的就不是原来的内容。服务端 `sanitize_json` 会把非有限浮点归一成 `null`，
   前端再按"空值"处理，于是界面上只剩空白 + 一句"解析成功"。
2. **时间轴退化**：`gps_week`/`gps_ms` 为空时所有行的 x 都是 0，曲线会挤在同一时刻。

现在这两类都会自己说出来，而不是留一片空白：

- 前端：一条曲线都画不出来时，横幅直接列出"哪些字段组全为空"（`emptyViewHint`），并指向
  `tests/diagnose_pcap.py`；
- 前端：`requestAnimationFrame`/`ResizeObserver`/`IntersectionObserver` 回调里抛出的异常以前
  只留在控制台（界面表现就是"数据加载成功但图表全空白"），现在由 `setupRuntimeErrorReporting`
  兜住并显示到横幅上（`window.onerror` + `unhandledrejection`）；
- 命令行：`python tests/diagnose_pcap.py <文件>` 打印 GSOF49/GSOF1/GSOF50/GGA/无效记录计数、每个字段组
  的有效行数与 NaN 计数，并直接判定"能不能画图"。

### 图表"画出来了没有"必须用真浏览器验证

`node tests/test_frontend_faults.js` 里的 DOM/Canvas 都是 stub，只能证明"数据进了 state、图表对象建好了"，
证明不了画布上真的有内容。曾经有这样一个 bug 只在这种地方显形：

> 数据加载完成时，**不在视口里**的图表会被 `invalidateChart()` 置空，而 `IntersectionObserver`
> 只在"画布进入/离开视口"时补画。用户拖滚动条、快速滚轮或点导航按钮**跳过去**的画布从未进入视口，
> 于是一直空白 —— 表现就是"解析完成后所有图表都不显示"，而状态栏、总数、表格全都正常。

修法是**把整套可见性缓存删掉**：`renderCharts()` 每次都画全部图表，不再有"只画视口内"的分支
（省下的那几百毫秒不值得这个风险）。回归用例见 `tests/test_frontend_faults.js` 的 [11]；真浏览器验证用：

```powershell
node tests/check_browser_render.js --data "D:\你的采集目录" --count 28
```

它自己起一个临时服务 + 无头 Chrome，用 CDP 把真实文件塞进文件选择框，等解析完成后
**逐张读取画布像素**（`painted` = 与背景色不同的像素数）并断言每张图都画了东西，同时收集页面里的
脚本错误；不需要人工点选，也不依赖已在运行的服务（`--app <url>` 可以指向已经跑着的实例）。

仍然保留的取舍（不是缺陷，是有意为之）：

1. **文件夹轮询仍是整目录重传重解**：签名一变就重跑全部文件，没有做"只解析新增文件"的增量缓存。
   文件多时这一下会重新走一遍全部耗时（见“使用”一节）。签名现在只认文件集合、且有 20 秒冷却，
   所以不会再被"正在录制的文件在不断变大"拖成无限重载；但 300 个文件的新增一次仍要重解析整目录。
2. **坏文件的行不会进表格**：整份文件失败时它的行无处可来，只能进 `errors`；同一文件内单条畸形
   记录会被跳过并计入 `invalid_records`，不影响该文件其它行。

### 与原项目 AP18 解析器的关系

**`parse_ap18_pcap.py` 一行未改**，`/api/parse` 的逻辑也没有改动：

- 有效里程只是**以库的方式 import** `decode_file()` 拿解析结果，解析行为完全不变；
- `ap18_visualizer.py` 只**新增**了 `/api/mileage`、`/api/mileage/scan` 两个路由与 handler；
- `web/index.html` 只多一个「有效里程」按钮，`web/app.js` 只多一行开窗绑定；
- 回归测试 `tests/test_parse_api.py` 会把 `/api/parse` 的 rows 与直连 `decode_file()` 逐字段比对，
  1,800 行全部一致（本次改动后依然全绿）。

唯一需要留意的副作用：`import ap18_mileage` 会把 `mileage/` 目录加进 `sys.path`
（与 verify_service 的部署方式一致），以便复用 `mileage/main.py` 等扁平模块。本仓库里没有
其它同名的 `config` / `main` / `utils` 模块，因此不会遮蔽任何东西；但把这份代码嵌进别的
工程时要注意这层 `sys.path` 影响。

### 资源与并发

- pcap 解码复用 `/api/parse` 已有的进程池（默认 `min(CPU, 8)` 个进程），不另开一套；
- 单次请求最多解析 5000 个 pcap（`ap18_mileage.DEFAULT_MAX_PCAP_FILES`），批量刷写最多 200 天；
- 批量刷写是前端逐天调用 `/api/mileage`，某一天失败不会影响其它天。

### 惯导数据兼容（俄罗斯 E5 / rtkimu 等）

除 AP18 pcap 外，也能直接吃这类惯导目录（例如
`\\192.168.20.206\logs_new\020_E5-001\Russia\Overseas\10\20261003`）：

```text
20261003/
├─ qinji/20261003.txt              NovAtel 二进制原始观测 → 自动识别并跳过（无位置解算）
├─ rtkimu_qj_7683/20261003.txt     $GPFPD 文本轨迹，100 Hz → 作为轨迹来源
├─ vin_device_2M/                  M57-2M_E5-001_20261003_20261003_180047_017.vin …
└─ vin_device_8M/
```

与标准数据相比，这里做了 5 处适配（都只对「变种」生效，不影响现有 AP18 / 中国 GPFPD 数据）：

| 差异 | 处理 |
| --- | --- |
| 校验和是**累加和（含 `$`）**，不是标准 NMEA 异或 | `_nmea_checksum_valid` 同时接受两种；按「异或不通过、累加和通过」自动判定变种 |
| 状态码是 **08（组合导航正常）/ 09（静止/零速修正）** | 变种走独立状态码集合（08 稳定、09 不稳定），标准 GPFPD 仍是 1/2/11/12 |
| GPFPD 的周/周内秒是 **GPS 时** | 换算成 Unix 秒时加 GPS 纪元（1980-01-06）并扣 18 秒闰秒，否则和文件名时间差 10.7 年 |
| 文件名日期出现两次（`..._20261003_20261003_180047_017.vin`） | 取**末尾**的「日期_时刻_序号」，组起始时刻 = 时刻 + 序号×60 秒 |
| 设备文件名时间 | 实测「文件名时刻 + 61 秒 == 文件 mtime，mtime 按本机时区显示」⇒ **设备时钟就是本机时区（北京时间）**，默认不平移；确有例外时用 `config.DEVICE_TIMEZONE_OFFSET_HOURS` 覆盖 |

另外：轨迹文件在子目录里也能找到（顶层没有 txt/csv 时会扫一层子目录，并按内容嗅探
`$GPFPD`/`$GGA`/CSV，二进制文件跳过）；设备目录会**递归扫 4 层**（部分日期的数据放在
`vin_device_2M/20260923-1_2M/` 这类会话子目录里）；100 Hz 数据会按需抽稀（默认上限 40 万点，
里程用 Vincenty 逐段精确累加，误差可忽略）。

实测（`20261003`，5.64 小时 / 406.7 km）：

| 指标 | 结果 |
| --- | --- |
| 有效里程（GPS∩2M∩8M 三者交集） | 64.005 km（16.4%） |
| GPS 稳定 / 总轨迹 | 389.234 km / 406.678 km |
| 2M / 8M 覆盖里程 | 64.005 km / 389.234 km |
| 设备时区 | 本机时区 UTC+8（不平移） |
| 耗时 | 约 105 s（含 NAS 上 219 MB 轨迹读取与 2475 个设备文件扫描） |

## 使用

在页面左侧“从前端导入 PCAP”区域：

1. 点击“选择多个文件”，一次选择一个或多个 `.pcap`（或 `.txt`）文件；或
2. 点击“选择文件夹”，选择包含 `.pcap` / `.txt` 的目录。

选择完成后会**自动开始上传并解析**，无需再点击加载按钮。随后左侧文件列表、地图、曲线和原始表格都会切换到这些数据。上传期间两个选择按钮会暂时禁用，状态区会提示进度与结果。

- “清空并刷新”只清空**当前浏览器**的数据，不影响其它浏览者，也不会删除磁盘原文件。
- 如果浏览器支持目录访问权限（Chrome/Edge），所选文件夹会自动每 3 秒检查**新增/删除的文件**并自动重新解析；不支持的浏览器需在文件夹新增内容后重新选择一次文件夹。两个边界要注意：
  - **正在录制的文件变大不算变化**（签名只比对文件集合，不比对 size/mtime）。以前比 size+mtime 时，录制中的 pcap 每写一点就让签名变化，于是每次轮询都触发"整目录重传重解"，上一次 80 多秒刚结束就立刻开始下一次，页面永远停在"正在解析"、图表一直不显示。
  - **两次自动重解析之间至少间隔 20 秒**（冷却期），保证页面有空闲时间把图表画出来；代价是新增文件最多延迟约 20 秒才自动出现。
  - 仍然是**整目录重传重解**（不是只解析新增文件），文件多时这一下会重新走一遍全部耗时。
- 下载按钮会把原始文件（PCAP/TXT）从当前浏览器会话重新下载；切换为单个文件视图后可用。
- 局域网访问时文件会上传到运行服务的这台电脑做**一次性解析**，请只选择可信文件并只在可信网络中使用。

## 有效里程（独立页面）

首页右上角「有效里程」按钮会**开一个新窗口**打开 `/mileage.html`；也可以直接在地址栏访问
`http://127.0.0.1:8765/mileage.html`。它和上面的轨迹分析互不影响：

- 这里**不上传文件**，而是填一个**服务器上可直接读取的数据目录**（如 `D:\data\20260917`、
  `/mnt/logs_new/.../20260917`；Windows 共享路径由后端按 CIFS 挂载表自动映射）。
- 目录里要有：AP18 pcap（`AP18/*.pcap` 或顶层 `*.pcap`），以及 2M / 8M 设备目录
  （目录名里带 `2M` / `8M`，如 `M57_2M_.../`、`M57_8M_.../`）。
- **轨迹解析复用原项目的 `parse_ap18_pcap`（GSOF49）**，与「原始记录表」用的是同一份解析；
  里程、覆盖交集、异常判定全部由 `mileage/` 里的计算器完成，没有第二套算法。

### 四个里程口径

| 指标 | 含义 |
| --- | --- |
| **有效里程（页面最前面的大字）** | **GPS 稳定 ∩ 2M 录制 ∩ 8M 录制**（三者全覆盖的交集）；这是最终要看的口径，三者缺一即为 0 |
| GPS 稳定里程 | 相邻点 GNSS 状态都稳定的段长度之和；GSOF49 的 GNSS 状态 ∈ {SPS, 差分 GPS, PPS, RTK 固定, RTK 浮动}，无定位(0) 与 DR 推算(6) 不算 |
| 2M 覆盖里程 | 落在 2M 录制时段内的 GPS 稳定里程 |
| 8M 覆盖里程 | 落在 8M 录制时段内的 GPS 稳定里程 |
| 任一覆盖里程（并集） | 2M 或 8M 任一在录的 GPS 稳定里程；只作参考，**不计入有效里程** |

另外还会给出：总轨迹长度、无覆盖里程、覆盖率百分比。

> **占位文件不计入覆盖**：采集失败时设备目录里会留下 0 字节或几字节的文件
> （实测 `vin_device_8M` 里 4424 个文件总共只有 6.6 MB，`.vin` 4 字节、`.blf` 308 字节）。
> 小于 `MIN_DEVICE_FILE_BYTES`（64 KB）的文件只算「占位」，不产生覆盖时段，
> 结果里会把数量报出来（`ignored_small_files`），避免把无效数据算成有效里程。

### 覆盖图形对比

`/mileage.html` 有两张对比图（浏览器本地 canvas 绘制，无第三方图表库）：

- **覆盖里程对比**（横向柱状）：GPS 稳定 / 2M 覆盖 / 8M 覆盖 / **有效里程（三者交集）** /
  任一覆盖（2M∪8M）/ 无覆盖，直接看各口径差多少；
- **覆盖时间轴对比**（甘特图）：四条轨道分别是 GPS 稳定段、2M 录制、8M 录制、
  两者同时录制，横轴为时间，一眼看出哪段时间只有单侧相机在录。

时间轴数据由后端合并后回传（`coverage.timeline`，epoch 秒）：
一百赫兹的稳定点逐段回传会有几万个矩形，合并后通常只剩几段。

### 两个 sheet：单日刷写 / 批量刷写

`/mileage.html` 顶部有「单日刷写」「批量刷写」两个标签页（sheet），互不干扰：

- **单日刷写**：填一个日期目录 → 看有效里程、四张卡、两张对比图、覆盖明细；
  下面还有「历史记录」检索区。算过的天会直接读数据库（秒出），需要更新点「重算」。
- **批量刷写**：填父目录 → 扫描日期 → 勾选 → 逐天刷写；扫描结果里会标注

当前 sheet、输入过的目录都会记在浏览器 localStorage，刷新页面自动恢复。

### 结果数据库（SQLite）：刷新不丢，增量 + 历史检索

结果持久化在服务端 SQLite（默认 `<仓库>/data/mileage.db`，可用 `--db` 或
`AP18_MILEAGE_DB` 覆盖；`data/` 已在 `.gitignore` 里）：

| 表 | 用途 |
| --- | --- |
| `day_analysis` | 每个「数据目录 + 日期」一条最新结果（唯一索引 upsert），含汇总列和完整结果 JSON |
| `analysis_history` | 每次计算/重算追加一条，审计与回溯用 |

行为：

- `POST /api/mileage` 默认**先查库**：命中就直接返回（响应里 `cached: true`，
  带 `computed_at`），不再解析 pcap；`{"refresh": true}` 强制重算并覆盖。
- `POST /api/mileage/scan` 会给每个日期标注 `analyzed` / `computed_at` /
  `cached_effective_m`，前端据此做增量默认勾选。
- `GET /api/mileage/history?q=&limit=&offset=` 检索历史（按路径或日期关键字）；
- `GET /api/mileage/record?id=` 取某条完整结果（历史列表点「载入」直接还原图形）；
- `GET /api/mileage/stats` 数据库概览（天数、累计有效里程、最近计算时间）。

因为结果在服务端，**刷新页面、关闭浏览器、换一台电脑**打开页面都能查到；
页面加载时会自动拉取历史列表并显示在「单日刷写」下方。

- 批量：刷写结果标题右侧「导出 CSV」，逐天一行（日期/目录/有效里程/GPS/2M/8M/任一/无覆盖/

### 批量刷写

页面下方的「批量刷写」是一个父目录 → 日期子目录（`YYYYMMDD`）的工作流，
和旧 verify_service 的「批量刷里程」一致：

1. 填父目录，点「扫描日期」：后端只读目录结构做预检（不解析 pcap，很快），
   列出每个日期有没有轨迹 / 2M / 8M，并标注库里是否已有结果；
2. 默认勾选「可刷 + 未算」的天（增量）；可用「只选未算 / 全选可刷 / 全不选 / 反选」调整；
3. 点「开始刷写」：前端**逐天**调用 `/api/mileage`，每天都有真实进度，
   结果表按天列出来源（缓存/新算）、有效里程 / 2M∩8M / GPS 稳定 / 2M / 8M / 点数，
   并给出合计行和对比柱状图。每算完一天都会写库，中断了重跑也不会重复算。

逐天调用而不是一个长请求，好处是进度可见、单天失败不影响其它天、也不会被
一个几分钟的请求拖死。

**2M/8M 只是传感器录制时段**，本身没有「里程」：设备文件名里带「组起始时刻 + 组序号」，
一个文件约代表 60 秒有数据；取相邻段的时间中点判断「当时在不在录」。
AP18 的 GSOF49 没有 baseline 字段，所以 2M/8M 里程完全来自覆盖交集，
不来自轨迹里的小基线。

## 功能

- 全部文件或单个文件切换
- 多段 PCAP/TXT 轨迹按文件独立绘制，不跨文件强行连线；轨迹点按**屏幕分辨率抽样**（合计 20 万点预算，
  每文件至少 200 点，终点保留）：单个文件 6000 点早就超过像素分辨率，而 305 个文件全量是 180 万点，
  地图要为每个点建 LatLng、局部轨迹要为每个点做投影，每次重绘新分配几百 MB，会把浏览器标签页拖垮
  （表现就是"提示解析成功但图表全空/页面卡死"）。工具栏会写明"地图与轨迹 X / Y 点（按屏幕分辨率抽样）"
- 左侧文件列表支持多选/取消选择；选中轨迹显示彩色，未选中轨迹显示灰色，并与地图和局部轨迹联动。
  **所有时间曲线也是同一口径**：取消勾选某个文件后，该文件的数据在每张曲线图里都变成灰色（画在彩色曲线下面）；
  两遍之间按文件断笔，所以灰色不会跨过选中区间连出假直线（图例里不再写灰色说明）；
  勾选/取消勾选**不会重置地图视角**（只有换数据集或切换文件视图才 `fitBounds` 重新定位一次）
- 解析失败的文件也会列在左侧列表末尾（灰色 + 删除线 + "解析失败"），鼠标悬停显示失败原因；它没有复选框、
  不参与高亮计数，也不进图表/表格/下载 —— 只用来回答"我选的那个文件去哪了"
- 左侧文件名完整显示（自动换行，不再用省略号截断；悬停可看到原始文件名），侧栏宽度 300px（窄屏 262px）
- 地图标题栏可切换 Esri 街道/卫星底图，轨迹按原始 WGS84 经纬度叠加显示
- 局部平面轨迹、经纬度、高程、速度、姿态、角速度、加速度曲线
- GSOF1 定位使用卫星数曲线、范围和搜星评估（少于 5 颗提示卫星不足；搜星数优先取 GSOF1，设备不再输出 GSOF1 时自动回退到 NMEA GGA 第 7 字段，表格"搜星数来源"列标出实际来源）
- 差分龄期曲线与评估（NMEA GGA 第 13 字段）、差分参考站 ID；无差分输出或未匹配到 GGA 的行曲线断开
- GSOF50 的位置、速度、姿态 RMS **散点图**（每个采样点一个点，不做连线：没发送 GSOF50 的那一段直接没有点，）。RMS 是**间歇发送**的（约每 20 帧才带一次），所以：
  - 降采样时会为"在这份数据里真的稀疏"的字段整行保底（`downsampleRows`）：否则一张 12,000 点的
    抽样表里只有约 600 个 RMS 点，曲线又粗又不准，空缺处还会被连成假直线；
  - 折线类序列在**明显中断**处断开（`GAP_BREAK_FACTOR = 6`：超过该序列平均点距 6 倍才算中断），
    于是停发的那一段是空白，不会有一条斜线横穿过去；正常间歇（中间少一两帧）保持连续，不会画成虚线；
  - 渲染方式按"有没有缺口"选：**散点序列（RMS）永远只画点**；其他有缺口的序列走折线（带断开）；
    每行都有值的密集序列走包络带
- 位置 RMS 超限比例统计：只画在**"位置 RMS"图下方的那张明细表**里（概览区曾有重复的卡片，已去掉）：
  每个分量 × 每个阈值的"帧数 + 占比"，再加"运动帧（分母 > 5 km/h）""有 RMS 的帧""已排除 ≤ 5 km/h""总帧数"四列。
  **分子分母都只统计运动帧**：车速 > 5 km/h 且有位置 RMS 的帧（`RMS_MOVING_SPEED_KMH = 5`）。
  停车时 RMS 天然更小（实测北位置 RMS 中位 0.0288 m vs 运动 0.0379 m），混进分母会把动态精度指标做漂亮；
  ≤ 5 km/h 的静止/低速帧、未附带 GSOF50 的帧、以及读不到车速的帧都不计入分母（表尾给出各段帧数）。
  比较是严格大于，正好等于阈值的帧不算超限；界面标题与表尾都写明了这个车速口径。
  **百分比按严重程度高亮**：灰 = 0（无超限）· 蓝 = <1% · 橙 = ≥1% · 红 = ≥5%（配色含义写在面板底部）
- 曲线图例开关、悬停查看数据点（**时间窗口功能已移除**：图表与轨迹始终画全部数据）
- 密集曲线按像素列做 min/max 包络渲染：带子的厚度就是该时刻的真实幅度范围，尖峰不会被抽样丢掉；稀疏曲线仍按原样画折线。悬停与选中复用离屏缓存层，只有交互层重绘
- 全字段原始记录表，支持搜索和分页（全部在浏览器内完成）
- 原始 PCAP 时间戳与格式化 UTC 抓包时间并列显示
- 表格行悬停显示所属文件和定位信息，点击后固定提示，点击表格外关闭
- 选点联动：点击原始记录表的某一行或任意曲线图上的某个时刻后，所有时间曲线图同步显示红色竖直指示线和该记录的数据点，地图与局部平面轨迹标出该记录的实际位置，工具栏显示选中记录信息；再次点击同一点、“取消选中”按钮或点击空白处可取消
- 每个图表（地图、局部轨迹及全部时间曲线）标题栏都有“⤢ 放大”按钮，点击后在弹窗中以更大尺寸重新绘制该图表，时间曲线在放大视图中仍支持悬停查看数据点；点关闭按钮、弹窗外部或按 Esc 退出
- 当前 TXT / PCAP 原文件下载

地图直接使用解析结果中的 WGS84 纬度/经度，不进行 GCJ-02 或 BD-09 偏移转换。
Esri 街道/卫星底图需要网络连接，页面保留了地图版权标注；若底图不可用，仍可使用
下方局部平面轨迹和其他曲线。

搜星数优先读取 GSOF Type 1（Position Time）的“用于定位卫星数”。若设备输出配置里没有 GSOF1
（例如 2026-09 之后的抓包，解析头部的 `gsof1_satellite_records` 为 0），则自动回退到 NMEA GGA
第 7 字段；表格新增的“搜星数来源”列会标出该行的数值来自 GSOF1 还是 GGA。两者都没有时才显示“—”。

差分龄期（age of differential data）和差分参考站 ID 只存在于 NMEA GGA 的第 13 / 14 字段，
GSOF49/50 无法反推。GGA 只有 UTC 日内时刻、没有日期，因此按“日内秒”把每条 GGA 就近匹配到
GSOF49 行（容差 ±1.1 s；GGA 为 1 Hz 时刚好覆盖整条时间轴，超过容差说明 GGA 中断，对应行留空
而不会沿用陈旧值，跨零点按 24 h 环绕处理）。

GGA 定位质量（第 6 字段）不是差分/RTK（取值不在 2/4/5）时龄期本身没有意义，会标为
“未使用差分改正”；RTK 模式下不少接收机也会把龄期输出为空，此时标为“未输出差分龄期”，
不会被当成 0 显示成一条贴地的正常直线。

解析器同时接受 `$GPGGA` 和 `$GNGGA`（按第 3–5 字符 `GGA` 匹配，不锁死 talker），会校验
`*hh` 异或校验和，并支持“一个 UDP 包含多句”和“一句被拆到两个 UDP 包”的 NMEA 文本流。
历史 .txt 结果文件仍然可以导入，新增列会显示为空。
