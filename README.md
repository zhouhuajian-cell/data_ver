# AP18 参数融合图 + 里程分析平台 · SOP

> 面向采集/验证/交付一线的工作说明：**原来靠人工在源数据平台解析、跑脚本、看融合图、维护多维表格、发全员邮件、刷里程**，
> 现在收敛成「数据放好 → 平台自动扫/跑 → 人工只确认融合图 → 飞书自动通知 → 里程页面直接刷」。

- 访问入口（内网）：**http://10.2.248.6:8901/mileage.html**（本机：`http://127.0.0.1:8901/mileage.html`）
- 原始轨迹分析页：`http://10.2.248.6:8901/`
- 详细技术文档：[README_AP18_VISUALIZER.md](README_AP18_VISUALIZER.md) · 部署说明：[DEPLOY.md](DEPLOY.md)

## 1. 原来的流程（人工版）

| 序号 | 人工步骤 | 典型动作 | 痛点 |
| --- | --- | --- | --- |
| 1 | **去源数据平台解析数据** | 登录平台、找批次、下载/解析、拷到本地或共享盘 | 重复劳动；平台/目录结构变了就要重新找一个遍；容易漏数据集 |
| 2 | **人工执行数据质检脚本、查看参数融合图** | 开终端跑脚本、去产出目录逐张翻图、凭经验判断 | 结果散落在各人电脑；图看不全；不同人判断口径不一致；跑失败才发现数据不全 |
| 3 | **维护多维表格** | 手工记录日期、数据集、结论、备注、状态 | 容易漏记/重记；和实际数据对不上；查询、筛选、交接都靠人 |
| 4 | **发送全体邮件通知参数可用** | 写邮件、贴结论、群发 | 时效差；结论更新后要补发；不通过的原因没有沉淀 |
| 5 | **刷里程** | 人工跑里程脚本、汇总数字、出表 | 口径不统一；每次重跑耗时；历史结果难追溯 |

**一句话：每一步都要人重复操作和搬运，经验留在个人电脑和脑子里，过程不可追溯。**

## 2. 现在的工作流

```
   源数据获取（人工）
        │
        ▼
  平台解析数据（人工）
        │
        ▼
① 自动扫描平台解析后数据（平台）
   └─ 数据完整性预检：标定 yaml / pose / 相机帧数 / 雷达文件数 / 是否仍在写入
        │
        ▼
② 自动跑参数验证（平台）
   └─ 产出融合图/投影图/质检图，写入数据库，进入「库中已有结果」
        │
        ▼
③ 确认融合图：通过 / 不通过（人工）
   └─ 平台自动跳下一条；待办数量实时减少
        │
        ▼
④ 全部图给出结论后，弹窗确认验证结果（人工）→ 再确认是否发送飞书（人工）→ 卡片推送（程序）
        │
        ▼
⑤ 自动获取新增全量数据分析有效里程（程序）
```

## 3. 新旧流程对照

| 原人工步骤 | 现在由系统完成 | 人还需要做什么 |
| --- | --- | --- |
| ① 源数据平台解析 | 数据直接读共享盘；定时扫描父目录自动发现新数据集；批量扫描可一键列出待分析数据集 | 把数据按规范落到约定目录；必要时手工触发单日/批量扫描 |

| ⑤ 刷里程 | 里程页单日/批量直接刷，结果入库存档，命中缓存秒出，可导出 CSV；覆盖对比图和覆盖时间轴自动生成 | 输入目录/父目录、勾选日期 |

## 4. 这套工作流解决了什么

1. **把人工"搬运"变成系统"自动跑"**：自动扫描、预检、排队分析，人不用再登录平台解析、不用开终端跑脚本。
2. **每个数据集不漏、不重复**：扫描会跳过已分析/已有产出的数据集（增量），状态落库，避免漏数据集和重复跑。
3. **提前挡掉"白跑"**：数据没写完（30 分钟内还在修改）、缺标定/pose/相机帧/雷达文件的数据集会先判"不完整"跳过，不会跑完才发现失败。
4. **人工只保留必须由人判断的一步**：看参数融合图给结论；抽样规则固定（每组投影均匀抽 5 张 + 质检图全量），口径统一。
5. **不通过必须留原因**：前端弹窗必填、后端强制校验，原因落库并随飞书推送，问题可回溯、可统计。
6. **多维表格下线**：「库中已有结果 + 各项目待办」替代手工表格，随时可查、可筛选、可按日期倒序，交接不依赖个人电脑。
7. **通知两步确认、可追溯**：先确认验证结果、再决定是否发飞书，卡片包含数据集、结果、分组统计、不通过项及原因、数据采集日期、确认时间；不重复推送。
8. **里程口径统一**：有效里程 = GPS 稳定 ∩ 2M 录制 ∩ 8M 录制；单日/批量都走同一套计算器，结果入库、可导出、可复查。
9. **全流程可分享**：结果都在服务端数据库，换台电脑/刷新页面不丢；历史列表点「载入确认图」即可回到当时的图。

## 5. SOP 详细步骤

### 5.0 角色与前提

| 角色 | 职责 |
| --- | --- |
| 数据管理员 | 把源数据按规范落到共享盘；维护自动扫描路径配置 |
| 验证工程师 | 在平台上确认参数融合图、给出通过/不通过及原因 |
| 交付/项目负责人 | 确认飞书结论；查看里程与整体进度 |

前提：浏览器能访问内网 `http://10.2.248.6:8901`；服务无登录鉴权，**只在内网使用**。

### 5.1 数据准备（对应原步骤①）

参数验证数据集目录要求：

```
<数据集目录>/
├── parameter_yaml/<标定日期>/*.yaml     # 必须
├── cam_st_x2f_front/…                    # 至少一个 cam_* 目录，帧数达到阈值
├── lidar_*/…                             # 至少一个 lidar_* 目录，文件数达到阈值
├── rtkimu_qj_7683/*.pose                 # 必须（定位文件）
└── FrameMap.json                         # 可选；已有则复用，不重复生成
```

里程数据目录要求：

```
<日期目录>/
├── AP18/*.pcap  或  顶层 *.pcap          # 轨迹来源（GSOF49/GGA）
├── *2M*/                                 # 2M 设备目录（目录名带 2M）
└── *8M*/                                 # 8M 设备目录（目录名带 8M）
```

注意事项：

- 服务器直接把 **Windows 共享路径自动映射**为 Linux 路径，例如 `\\192.168.20.206\Data_Platform\...` → `/mnt/Data_Platform/...`，两种写法都能填。
- 2M/8M 只是**录制时段**，本身没有里程概念；小于 64KB 的占位文件不算有效录制。
- 名称里带日期的数据集（如 `137657_E5-001_yanzhen_20261017`）会被自动识别地区/车型与数据采集日期。

### 5.2 让数据进入系统（对应原步骤①）

三种方式，日常用自动扫描即可：

1. **自动扫描（推荐，无需人工）**
   - 服务器定时任务 `ap18-auto-verify.timer`：启动后 5 分钟首次执行，之后**每 1 小时**一轮；
   - 单轮最多分析 4 个新数据集；数据最近修改未满 **30 分钟**视为仍在写入，跳过；
   - 扫描路径配置：`data/auto_verify_roots.txt`（一行一个父目录，`#` 注释）；
     每行可加 `since=YYYYMMDD`，只分析该日期及之后的数据集（更早的忽略），例如：
     ```
     /mnt/Data_Platform/.../E5-001_VSLAM_yanzheng/E5-001
     /mnt/Data_Platform/.../LYNK01-001_VSlam_InternalPro/LYNK01-001 since=20261021
     /mnt/Data_Platform/.../EX5-001_VSLAM_jiaobenyanzheng/EX5-001 since=20261021
     ```
   - 兼容不同车型：定位目录按 `rtkimu*` 前缀识别（E5 的 `rtkimu_qj_7683`、LYNK 的 `rtkimu_lvx_125` 等），雷达文件支持 `.pcd/.bin/.las/.laz`；
   - **新增数据推送（流程）**：某个新数据集分析完成后**立刻**推飞书卡片（含项目/车型、数据集、数据采集日期、分析完成时间、平台链接，并按项目 @ 责任人），提醒去确认融合图；一次扫描有多个新数据集则合并成一张卡片；`--no-notify` 可关闭；
   - 日志：`logs/auto_verify.log`；
   - 只检查不分析：`python tools/auto_verify_scan.py --dry-run`。

2. **单日手工**：进入「单日参数验证」sheet，填数据集目录 → 「开始验证」（或「查看/确认交付图」直接读已有产出）。

3. **批量手工**：进入「批量参数验证」sheet，填父目录 → 「扫描数据集」→ 系统列出含 `parameter_yaml` 的数据集并标注「已分析/未分析」→ 勾选（可用「只选未分析」「全选」「全不选」）→ 「开始批量验证」。

> 平台不会往数据目录写文件；验证产出统一落在服务端 `data/verify/task_<时间>_<随机>/`。

### 5.3 自动预检（新增能力，无需人工）

系统在分析前检查，不满足则跳过并在状态里写明原因：

- 缺 `parameter_yaml` 标定文件；
- 缺 `rtkimu_qj_7683/*.pose`；
- 相机目录帧数不足（默认 10 帧）/ 雷达目录文件数不足（默认 3 个）；
- 数据仍在写入（最近修改 < 30 分钟）；
- 数据目录里已有 `framemap_dataquality_projection` 产出 → 登记为「已有产出」，直接进历史库，不重复分析。

### 5.4 参数验证执行（对应原步骤②）

- 默认选项：**数据质检 ✔**、**外参校验 / 反投影 ✔**；点云完整重投影默认关（很慢，按需开启）。
- 后台串行执行，页面有进度条与日志；单个数据集通常几分钟内完成（取决于帧数/磁盘）。
- 跑完自动加载「参数融合图需人工确认」面板；也可以在「库中已有结果」里点「载入确认图」。

### 5.5 人工确认参数融合图（对应原步骤②的判断环节）

1. 面板标题：**参数融合图需人工确认**；下方显示**数据采集日期**（取数据实际采集时间，不是目录名）。
2. 分组与抽样规则：
   - `front(x2f) 点云投影叠加图`：从全部投影图中按时间戳均匀抽 **5 张**；
   - `front7(x8d) 点云投影叠加图`：同样抽 **5 张**；
   - `数据质检`：图表**全部展示**（通常 5 张）；
   - 合计通常 15 张，右上角汇总 `通过 x · 不通过 y · 待确认 z`。
   - **换 5 张**：投影图分组标题右侧有「换 5 张」按钮，点一下会从该组全部投影图里按时间戳**随机重新抽 5 张**
     （自动避开当前已显示的），用来避开空旷、无明显标志物、不好判断的路段；抽完需要重新确认这 5 张。
3. 逐张操作：
   - 点「通过」：直接记录；
   - 点「不通过」：弹出「填写问题原因」窗口，**必须填写**，空内容会被拦下；填写后保存，缩略图下方显示红色 `原因：…`；
   - 可点图片放大查看（滚轮缩放、拖动平移、双击/Esc 退出）；
   - 也可勾选多张后用「通过所选 / 不通过所选」（失败原因应用到所选全部）。
4. 底部导航：`上一条` · `第 N/M 条` · `下一条` · `☑ 评完自动下一条`。
   - 全部图都给出结论后，若勾着「评完自动下一条」，会跳到队列里的下一天；队列走完会自动加载库里下一页。
5. 所有图都有结论才算这一天评完；`待确认` 不为 0 时不会触发飞书推送。

### 5.6 结果确认与飞书通知（对应原步骤④）

一天的全部图给出结论后，会连续走**两步确认**：

1. **验证结果确认**：弹窗显示通过/不通过/合计和飞书卡片预览；核对无误点「确认」（点「取消」则结果保存但不发送）。
2. **是否把验证结果发送飞书？**：点「确认」后再次弹窗，选择：
   - 「发送飞书」→ 推送卡片；
   - 「暂不发送」→ 结果保存，不推送。

卡片内容包含：地区 · 车型 · 结果（参数验证通过/不通过）、数据集、结果统计、分组统计、不通过项、**不通过原因**、数据采集时间、确认时间。

- **同一条结果不会重复推送**；修改结论或原因后，会重新弹窗允许再次推送。
- 发送配置：`data/feishu_webhook.txt`（或环境变量 `AP18_FEISHU_WEBHOOK`），换 webhook 只需改这个文件。
- **群消息 @ 人**：把各项目负责人的 open_id 配到 `data/feishu_mentions.json`（格式见 `tools/feishu_mentions.example.json`），
  参数验证结果卡片、有效率预警会按项目 @ 对应负责人。自定义机器人（webhook）只支持用 **open_id** @人，不能按姓名 @。

### 5.7 刷里程（对应原步骤⑤）

进入「单日里程分析」或「批量里程分析」sheet：

1. **单日**：填日期目录 → 「开始分析」；命中数据库缓存秒出，需要最新结果点「重算」。
2. **批量**：填父目录 → 「扫描日期」→ 勾选（默认只勾「可刷 + 未算」的增量）→ 「开始刷写」。
3. 结果口径：
   - **有效里程** = GPS 稳定 ∩ 2M 录制 ∩ 8M 录制（页面最前面的大字，最终口径）；
   - 另有 GPS 稳定里程、2M/8M 覆盖里程、任一覆盖里程、无覆盖里程、覆盖率；
   - 覆盖对比柱状图、覆盖时间轴（甘特图）、覆盖明细表。
4. 「导出 CSV」：单日/批量均可导出，UTF-8 BOM，Excel 直接打开不乱码。
5. 历史结果在「库中已有结果」可检索、载入（与参数验证各自独立）。

### 5.8 结果查询、待办与交付包（对应原步骤③）

- **各项目待办**（页面顶部）：按地区/车型汇总 `待确认参数验证`、`已验证`、`里程天数`、最近更新时间；每 60 秒自动刷新。
- **库中已有结果**（两个验证 sheet 各一份）：
  - 列：日期 / 地区 / 分析时间 / 分析状态 / 验证时间 / 验证状态 / 源数据路径 / 操作；
  - 筛选：全局「项目」筛选、时间范围（全部时间/本月/上月/自定义范围）、验证状态（已验证/未验证）、路径关键词搜索；
  - 按数据采集日期倒序，分页；
  - 操作：**载入确认图**（回到该数据集继续/复查）、**生成交付包 / 下载交付包**。
- 交付包：生成后可在历史列表直接下载，用于归档/交付；zip 放在服务端交付目录或数据目录 `delivery_package/` 下。

### 5.9 待办汇总提醒（自动，10/15/19 点）

参数验证是每天都要看的活，平台会定时把待办汇总推到飞书群：

- **频率**：服务器 systemd 定时器 `ap18-todo-notify.timer`，**每天 10:00 / 15:00 / 19:00** 各一轮（每 4 小时；07:00、23:00 和夜间不推送）；
- **内容**：只推**各项目待办汇总**，每个项目两行，**不列具体数据集明细**（明细到平台上看）：
  - `参数验证：待确认 X 天 · 已完成 Y 天 · 累计 Z 天`
  - `有效里程：新增 X 天 · 已有 Y 天 · 累计 Z 天`（新增 = 上次发送后新算出来的里程天数）
- **发送规则**：**只要有待办就发**（标题为「新增 N 个 · 共 M 个待确认」或「剩余 M 个待确认」）；没有待办才跳过；加 `--only-new` 可恢复「只有新增才发」；
- **日志**：`logs/todo_notify.log`；状态文件 `data/todo_notify_state.json`（记录已提醒过的待办）；
- **手工测试**：
  ```bash
  python tools/todo_notify.py --dry-run   # 只看内容，不发
  python tools/todo_notify.py --force     # 没有待办也发一次汇总
  ```

### 5.10 里程自动分析（自动，每 24 小时）

> **当前状态：已启用（每天遍历一次）**，只处理 20261023 之后的新数据；已有历史数据不搬旧账。

里程刷写也做成了定时自动跑，直接复用页面上的同一套里程计算器：

- **固定路径**（`data/auto_mileage_roots.txt`）：
  - 南美：`/mnt/logs_new/019_EX5-001/South_america/BR since=20261023`
  - 独联体：`/mnt/logs_new/020_E5-001/Russia/Overseas since=20261023`
  - 欧洲：`/mnt/logs_new/018_LYNK01-001/overseas/Europe since=20261023`
- **频率**：systemd 定时器 `ap18-auto-mileage.timer`，**每天 20:00** 遍历一轮（`Persistent=true`，错过的会在下次补跑），单轮最多 20 天；
- **识别规则**：父目录下递归（最多 4 层）找 8 位日期目录（兼容 `BR/2026/8/20260805`、`Europe/CZ/20260729`、`Overseas/10/20261001` 等布局）；「未验证 / 不可用 / 其他文件 / 标定文件 / 模板 / error」等目录跳过；
- **完整性预检**：日期目录缺**轨迹 / 2M / 8M** 任一项 → 记日志「数据不完整，跳过」，不分析；
- **增量**：库里已有结果且数据没再变化 → 跳过；新目录或数据有更新 → 自动分析并写库（页面「库中已有结果」直接可见）；
- **稳定性**：最近 30 分钟内还在修改的目录先跳过（防止边录边算）；失败目录 6 小时内不重试；
- **日志**：`logs/auto_mileage.log`；失败状态 `data/auto_mileage_state.json`；
- **手工测试**：
  ```bash
  python tools/auto_mileage_scan.py --dry-run          # 只扫描、打印会算哪些天
  python tools/auto_mileage_scan.py --limit 1          # 只算一天
  python tools/auto_mileage_scan.py --root /mnt/...     # 临时指定父目录
  python tools/auto_mileage_scan.py --force             # 忽略缓存全部重算
  ```

> 这两个自动任务（待办提醒、里程自动分析）都通过 `data/*.txt` + systemd timer 留了配置口子：以后要加路径、改频率，只改配置/定时器，不用改代码。

### 5.11 里程有效率预警（自动，每 4 小时）

有效率偏低时自动汇总推送飞书，并说明原因：

- **口径**：`有效率 = 有效里程（GPS稳定 ∩ 2M ∩ 8M）/ GPS稳定里程 × 100%`，低于 **90%** 视为偏低；
- **频率**：服务器 systemd 定时器 `ap18-mileage-alert.timer`，启动后 25 分钟首次、之后**每 4 小时**一轮；
- **增量不重复**：按「数据目录 + 日期」去重，同一天只推一次；有新增低有效率天才会发；
- **内容**：只按项目汇总（不列具体日期明细，明细在平台看）：每个项目一行 `新增 X 天 · 累计 Y 天 · 平均有效率 · 最低有效率`，再加一行 `主要问题`（原因归类计数），例如：
  - 2M 或 8M 目录里只有占位文件（<64KB），没有真实录制；
  - 2M / 8M 录制覆盖不足（只覆盖 GPS 稳定里程的 x%）；
  - 2M 与 8M 录制时段几乎不重叠；
  - GPS 稳定里程为 0、无覆盖里程等；另附累计天数与口径说明；
- **日志**：`logs/mileage_alert.log`；状态文件 `data/mileage_alert_state.json`；
- **手工测试**：
  ```bash
  python tools/mileage_ratio_alert.py --dry-run        # 只看内容，不发
  python tools/mileage_ratio_alert.py --force          # 强制发一次
  python tools/mileage_ratio_alert.py --threshold 80   # 改阈值
  ```

### 5.12 海外数据看板

页面顶部第一个入口是整合后的 **海外数据看板**（里程 + 参数验证，默认打开）：

- 顶部 6 个指标卡：有效里程合计、GPS稳定里程、里程天数（含低有效率天数）、参数验证数据集（含待确认/无交付图）、验证通过（含不通过/已验证）、参数验证通过率；
- 两个**仪表盘**：平均有效里程率、参数验证通过率（<50% 红、<90% 橙、≥90% 青）；
- 四张明细表：里程按项目、参数验证按项目、里程最近 14 天、参数验证最近记录（含最近更新时间）；
- 顶部「项目」筛选和时间范围（全部时间/本月/上月/自定义范围）同时作用于整个看板。

参数验证的明细列表仍在「单日参数验证 / 批量参数验证」里的 **库中已有结果**（含分析时间、验证时间等最新更新时间），
并支持按「验证通过 / 不通过 / 已验证 / 未验证」筛选；时间筛选**按数据采集日期**：全部时间 / 本月 / 上月 / 自定义范围（开始~结束）。

看板数据接口：`GET /api/dashboard/mileage?days=&region=`、`GET /api/dashboard/verify?days=&region=`。

### 5.13 异常与处理

| 现象 | 原因 | 处理 |
| --- | --- | --- |
| 扫描结果里标「未完成」 | 缺标定/pose、相机帧数或雷达文件不足、数据仍在写入 | 等数据写完或补齐文件后重扫；看扫描表「说明」列 |
| 预检提示「缺 parameter_yaml」 | 目录结构不对或不是验证数据集 | 核对数据集目录规范；换正确的父目录 |
| 批量结果里某天「失败」 | 数据集损坏、脚本执行异常 | 展开错误信息；重新单独跑该数据集；必要时排查数据 |
| 页面提示「没有找到验证产出目录」 | 还没跑过验证且目录里无已有产出 | 先「开始验证」；或确认路径是否正确 |
| 任务一直转圈/服务不可用 | 服务进程异常 | 服务器 `systemctl status ap18-visualizer`；本机 `status.bat`，必要时 `start.bat`/`update.bat` |
| 飞书没收到 | webhook 失效、还有图未确认、结果未变化 | 检查 `data/feishu_webhook.txt`；确认汇总 `待确认 0`；结果未变化属正常不重推 |
| 里程为 0 或明显偏小 | 目录缺 2M/8M、命名不合规、pcap 时间异常 | 核对 2M/8M 目录名、pcap 与设备文件时间；看「提示/问题」区 |

## 8. FAQ

**Q：为什么日期显示的不是目录名里的日期？**
A：参数融合图上方显示的是**数据实际采集日期**，取数据本身的时间戳（FrameMap 首帧/相机文件名），目录名与真实采集日期偶尔会差一天。

**Q：不通过能不能不写原因？**
A：不能。前端弹窗必填，后端接口也会拒绝（返回 400），原因会随飞书推送。

**Q：自动扫描会不会重复跑？**
A：不会。已分析成功、已有产出、以及 6 小时内失败过的数据集都会跳过；单轮还有数量上限，避免一次压垮服务器。

**Q：库里已经有的数据还要重跑吗？**
A：默认直接读库（秒出/直接确认图）；需要更新时用「重算」或批量里的强制重算/「开始验证」。

**Q：2M/8M 覆盖里程为 0？**
A：2M/8M 是录制时段，不是里程来源；检查目录名是否带 `2M`/`8M`、文件是否只有占位（<64KB）、以及 pcap 时间是否正常。
