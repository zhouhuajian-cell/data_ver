# 平台里程解析逻辑（汇报/答辩说明）
> 对应代码：`ap18_mileage.py`、`mileage/main.py`、`mileage/verify_service/mileage.py`、`mileage/config.py`

## 0. 30 秒版口径（先抛结论）

> 平台算的不是「轨迹总长度」，而是 **有效里程 = GPS 覆盖里程 ∩ 2M 录制时段 ∩ 8M 录制时段**。
> 先把轨迹解析成点，剔除 GPS 无解/纯 DR、时间异常和跳点，得到「GPS 覆盖里程」；再按 2M/8M 设备文件的**录制时间段**去覆盖它，只有三者同时在录/在解的那一段才算「有效里程」。
> 有效率 = 有效里程 ÷ GPS 覆盖里程，低于 90% 前端标红，并会列出具体原因（缺 2M、缺 8M、时钟偏差、文件截断等）。

---

## 1. 数据从哪来

### 1.1 轨迹来源（按优先级）

1. **顶层文本轨迹**：数据目录顶层若有 `.txt` / `.csv`（NMEA GGA、GPFPD、GPFPD 变种、CSV），优先用它；
2. 顶层没有文本轨迹时，用 **AP18 pcap**（顶层或 `AP18/*.pcap`）：解析 GSOF49，含经纬度、速度、航向、GNSS 状态、GPS 时间；
3. 顶层既没有文本也没有 pcap 时，再**去子目录找文本轨迹**（例如俄罗斯 E5 的 `rtkimu_qj_7683/20260924.txt`）；
4. 都没有 → 报「无法计算里程」，并在页面「问题」栏说明原因。

> 轨迹文件会做「内容嗅探」：NMEA/GPFPD 文本才认；二进制、NovAtel 原始观测等只是**跳过并提示**，不会强行解析。

### 1.2 2M / 8M 设备数据

- 目录名含 `2M` / `8M`（如 `Vin_device_2M`、`Vin_device_8M`、`vin_device_2M`）；
- 文件名里带**组起始时刻**（如 `..._20260917_142635_110.pack`，末尾 `110` 是组序号）；
- 每组约 **60 秒**：文件代表 `[起始时刻, 起始时刻 + 60s]` 这段「设备在录」；
- 序号换算：真实时刻 = 文件名时刻 + 序号 × 60 秒；
- 小于 **64 KB** 的文件视为**占位文件**（采集失败留下的空壳），不算「在录」。

## 2. GPS 覆盖里程怎么算

### 2.1 GPS 覆盖点判定

一个点同时满足才算「GPS 覆盖」：

1. 有状态字段；
2. 解算状态在**白名单**内；
3. NMEA 校验和不是错误。

不同数据源白名单不同：

| 数据源 | 稳定码 |
| --- | --- |
| AP18 GSOF49（GNSS 状态） | 1 SPS / 2 差分GPS / 3 PPS / 4 RTK固定 / 5 RTK浮动 |
| GPFPD（解算状态） | 1 / 2 / 11 / 12（4/5 不在此体系） |
| GPFPD 变种（rtkimu，俄罗斯 E5 等） | 08 组合导航正常（09 静止/零速修正不作为稳定） |
| GGA（定位质量） | 1 / 2 / 4 / 5 |
| CSV（状态列） | 取 GPFPD 与 GGA 的并集 |

**排除**：0 无定位、6 DR 纯航位推算、校验和错误、没有状态字段的点。

### 2.2 相邻点成段

- 相邻两个点构成一段；
- 只有**两端都 GPS 覆盖**，且该段几何有效，才计入 GPS 覆盖里程；
- 异常段不计入：
  - 时间倒流/重复（Δt ≤ 0）；
  - 相邻点间隔 > **300 秒**（5 分钟）→ 切分新行程，跨行程段不计；
  - 跳点：距离 > `max(0.4 m, 150 km/h × Δt)` → 判为跳点，不计；
  - 2M/8M 基线类别切换的边界段（`2M↔8M` 或类别不一致）不计。

### 2.3 距离算法与抽稀

- 距离：WGS84 椭球 **Vincenty** 公式（两点间大地线距离）；
- 抽稀：单次最多 **40 万点**，超了按 `1/4、1/9...` 等间隔抽稀；只影响极小误差（相邻点距离仍是精确算的），页面「提示」会写明抽稀比例；
- 小时级/天级轨迹点数很多时，这是为了保证平台响应速度。

## 3. 2M / 8M 覆盖怎么算（核心）

1. 每个有效设备文件 → 一个 60 秒区间 `[t, t+60s)`；
2. 同一设备的所有区间合并（重叠/相邻合并）；
3. 对每一段「GPS 覆盖段」，取**段的时间中点**，判断是否落在 2M 区间、8M 区间内；
4. 只对 GPS 覆盖段统计，四类里程：
   - **2M 覆盖里程**：中点落在 2M 在录时段；
   - **8M 覆盖里程**：中点落在 8M 在录时段；
   - **任一覆盖**：2M ∪ 8M；
   - **无覆盖**：两个都不在录；
5. **有效里程 = 同时被 GPS 覆盖、2M、8M 三者覆盖的里程**（既不是「总轨迹」，也不是「任一路覆盖」）。

### 3.1 设备时钟偏差自动对齐

- 设备时钟可能不准（已遇到 8M 文件名时间整体偏移十几小时，导致与 2M/轨迹完全不重叠、有效里程为 0）；
- 平台发现 8M 与 2M 完全不重叠时，会按**整小时**自动试探偏移量，选重叠最大的方案对齐后重算；
- 结果「提示」会写明：`8M 设备时钟偏差 -13 小时，已自动对齐后计算覆盖`；
- 这样不用重新采集，先把有效里程算出来；但建议同步通知采集侧校准设备时间。

### 3.2 为什么 2M/8M 里程会不一样

因为两个设备**开录/停录时间不同**：2M 可能只录了某一段，8M 全程录；有效里程只认两者同时在录的部分。

## 4. 页面上的指标含义

| 指标 | 含义 |
| --- | --- |
| 有效里程 | GPS 覆盖 ∩ 2M ∩ 8M（最终口径） |
| GPS 覆盖 | 轨迹本身可用的里程（排除无解、DR、异常段） |
| 2M 覆盖 / 8M 覆盖 | 落在对应设备录制时段内的 GPS 覆盖里程 |
| 任一覆盖 | 2M 或 8M 至少一个在录 |
| 无覆盖 | 两个都不在录 |
| 有效里程率 | 有效里程 ÷ GPS 覆盖里程（<90% 前端标红） |
| 低有效率天 | 有效率 <90% 的天数（看板统计） |

> 同一项目同一天有多条结果时，库内按「有效里程高」保留一条，避免重复天数。

## 5. 秦冀惯导数据专项（重点准备）

### 5.1 目录长这样

```
20260924/
├── rtkimu_qj_7683/20260924.txt      ← 惯导输出的轨迹文本（NMEA / GPFPD 系）
├── qinji/20260924.txt               ← NovAtel 二进制原始观测，没有位置解算
├── Vin_device_2M/...                ← 2M 设备录制文件
├── Vin_device_8M/...                ← 8M 设备录制文件
└── qinji/...（其他）
```

### 5.2 平台怎么处理

- `rtkimu_qj_7683/*.txt`：嗅探为 **NMEA/GPFPD 轨迹**，正常解析 → 作为 GPS 轨迹来源；
- `qinji/*.txt`：二进制/非文本（如 NovAtel 原始观测），**没有位置解算**，平台跳过，并在「问题」栏提示：
  - `qinji/20260924.txt: 二进制/非文本（如 NovAtel 原始观测），没有位置解算，已跳过`
- 2M/8M 仍按设备目录文件时段算覆盖；
- 如果同时存在 AP18 pcap，则优先用 pcap（GSOF49）作为轨迹来源。

> 一句话：**秦冀的惯导数据我们用的是 rtkimu 输出的轨迹 txt；qinji 的原始二进制观测不参与轨迹解算**，这是数据本身决定的，不是平台漏读。

### 5.3 为什么某天有效率很低（举例 1.950 / 62.232 = 3.1%）

- GPS 覆盖 62.232 km（轨迹正常）；
- 2M 覆盖只有 1.950 km（2M 设备只录了很短一段）；
- 8M 覆盖 62.232 km（8M 全程在录）；
- 三者交集 = 2M 那一小段 1.950 km → 有效率 3.1%。

**结论**：不是轨迹解析错，而是 **2M 录制覆盖不足**（设备只录了一段/文件偏小/截断）。处理：补 2M 数据或确认 2M 录制策略，重算即可。

### 5.4 如果 2M/8M 都全、有效率还是 0

1. 是否有 `8M 设备时钟偏差 ... 已自动对齐` → 自动对齐后仍低，说明真实重叠就少；
2. 是否提示占位文件（<64KB）被忽略 → 设备当时没真正录；
3. 是否 pcap 截断/文件头异常 → 轨迹缺段；
4. 是否 2M/8M 目录名不符合规则（需含 `2M`/`8M`）→ 找不到设备数据；
5. 都没有 → 把数据目录和页面「问题」截图发我，查具体文件时段。

## 7. 常见追问 Q&A

**Q1：为什么不直接用轨迹总长度？**
A：总长度包含 GPS 无解、DR 推算、跳点、时间断裂等不可信部分，不能作为有效里程；平台先剔除这些再算。

**Q2：为什么有效里程不是 GPS 覆盖里程？**
A：有效里程还要求 2M 和 8M 同时录制；这是「三者全覆盖」的业务口径，用来保证里程对应的数据是可用的（有图/有雷达）。

**Q3：2M/8M 覆盖是按图像帧还是时间段？**
A：按**设备录制时间段**（每个文件 60 秒区间），不是逐帧图像；目的是判断「这段里程有没有对应设备数据」，不是算图像数量。

**Q4：为什么 2M 覆盖和 8M 覆盖差很多？**
A：两个设备开录/停录时间不同；也可能某个设备时钟偏、文件截断/占位。

**Q5：有效率多少算正常？**
A：没有固定值，取决于设备录制策略；平台阈值 90% 仅用于标红提醒。若长期低于 90%，优先查设备录制覆盖和时钟。

**Q6：8M 时钟偏差自动对齐靠谱吗？**
A：按整小时在 2M 时间段内找最大重叠，属于工程修正；会明示偏差小时数，便于复核。根子上建议校准设备时间。

**Q7：秦冀的惯导数据为什么被跳过？**
A：`qinji/*.txt` 是 NovAtel 二进制原始观测，没有位置解算，无法直接当轨迹；平台用的是 `rtkimu_qj_7683/*.txt`（NMEA/GPFPD）。

**Q8：重复日期怎么处理？**
A：同一项目（地区）同一天只保留有效里程最高的一条，避免重复统计天数。

**Q9：抽稀会不会算少？**
A：不会明显；抽稀只减少点数，相邻点距离仍按 Vincenty 精确算，页面提示里会说明比例。

**Q10：和供应商报的里程对不上？**
A：先对齐口径：供应商多为「GPS 总里程/原始里程」，平台是「GPS 覆盖 ∩ 2M ∩ 8M」有效里程；把两者的分项（GPS 覆盖、2M 覆盖、8M 覆盖）摆出来即可解释差异。

## 8. 一页速记

- 有效里程 = GPS覆盖 ∩ 2M ∩ 8M
- GPS覆盖 = 状态白名单 + 校验和OK + 两端稳定
- 异常剔除：Δt≤0、间隔>300s、跳点>max(0.4m,150km/h×Δt)、2M/8M边界
- 设备覆盖 = 文件名时段 + 每组60s + 序号×60；<64KB 不算
- 判定 = 段中点落在设备录制区间
- 时钟偏差 = 整小时自动对齐 + 提示
- 有效率 <90% = 前端标红
- 重复日期 = 保留有效里程最高
- 秦冀：rtkimu txt 可用；qinji 二进制观测跳过
